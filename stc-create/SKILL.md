# 救猫咪故事创作总编排

这套能力只有一个总目标：**帮助用户把同一个故事写好。** 完成流程、填满十五拍或生成一批文件，都不等于故事已经成立。

你的唯一职责是守住创作主线并组织改稿：判断作品现在最需要解决什么，把任务交给对应子 skill，检查新产物是否让故事更清楚、更有冲突、更有变化，再决定继续、回退或停下确认。你不在本文件里复刻各子 skill 的具体方法。

先读 `../references/story-creation-contract.md`。它只规定跨阶段不能漂移的故事核心与交接格式，不替代任何子 skill 的具体方法。

## 可调用能力

| 子 skill | 唯一任务 | 需要的主要输入 | 唯一交付物 |
|---|---|---|---|
| `stc-idea-check` | 把模糊方向发展成站得住的故事核心 | 方向、人物或一句点子 | 故事核心卡 |
| `stc-beatsheet` | 把故事核心铺成整体结构 | 已确认的故事核心卡 | 三个世界 + BS2 十五拍 |
| `stc-scene-cards` | 把节拍拆成可逐场写作的计划 | 已确认的节拍表 | 场景卡 |
| `stc-scene-write` | 把已确认的场景卡写成场景正文 | 场景卡、媒介和风格要求 | 场景正文 |
| `stc-diagnose` | 根据现有文本找问题并排序 | 完整稿或片段 | 证据化改稿单 |
| `stc-first-aid` | 解除创作者当下的“想不出来” | 明确的个人卡点 | 一个立即可做的解卡动作 |

依赖只从本编排器指向子 skill。子 skill 可以独立使用，不依赖本编排器才能完成任务。

## 编排流程

### 1. 先判断用户要创作还是改稿

- 从方向、人物或点子开始，一路做成完整作品 → 从当前已有阶段向下创作。
- 已有作品，只想知道问题 → 直接使用 `stc-diagnose`。
- 已有作品，要求实际修改、重写或“强势改稿” → 先诊断主要病根，再调用负责该层的创作 skill 执行修改；不能只交一份诊断报告就结束。

### 2. 找到当前阶段

先盘点用户已经有什么，不要求他重复已经提供过的内容：

- 只有方向、人物或模糊点子 → `stc-idea-check`
- 有确认过的故事核心，想搭大纲 → `stc-beatsheet`
- 有节拍表，想分场 → `stc-scene-cards`
- 有场景卡，想写正文 → `stc-scene-write`
- 有成稿或片段，想找问题 → `stc-diagnose`
- 不是文本出问题，而是创作者本人卡住 → `stc-first-aid`

如果用户明确只要一项，就直接交给该 skill，不套完整流程。

### 3. 守住同一个故事

每次交接前后只抓住四件事：

1. 观众主要跟随谁，为什么愿意继续跟随。
2. 主角眼前过不去的麻烦、想得到的东西和阻止他的力量是什么；表面目标背后是否扎到生存、饥饿、性、保护所爱之人、死亡恐惧等基本本能。
3. 主角从怎样的状态走向怎样的状态，变化是否由行动和代价造成。
4. 这个故事最终想让人感受到或明白什么，结尾是否兑现。

若一个前提本身没有成立，停在点子阶段处理；不要用更多设定、节拍或场景把它遮住。

### 4. 只调用当前一环

调用对应子 skill，并把已有上游产物作为输入。不要在本文件内复刻子 skill 的检查表，也不要在一个阶段提前完成下游工作。

如果宿主没有显式的 skill 间调用机制，但同套件目录可读，就读取对应兄弟目录的 `SKILL.md` 后执行；若依赖确实不可用，明确报告缺少哪个子 skill，不要凭本文件的摘要假装已经执行了它。

一次性交付时也要按顺序完成内部交接；可以省略等待，但不能省略产物。把未经用户确认的关键选择统一列为“暂定”，避免假装用户已经同意。

### 5. 检查交接，不检查手艺细节

本编排器只看三件事：

1. 当前阶段是否交付了表中规定的唯一产物。
2. 故事核心是否仍能回答原书主干五问和“原始吗”，后续有没有悄悄换主角、换目标、换原始驱动力、换主题或换结尾变化。
3. 下游所需的关键选择是否已经明确；若有多个会改变故事方向的选择，停在当前阶段让用户选。

具体的类型、节拍、场景和台词质量由对应子 skill 负责，本编排器不重复诊断。

### 6. 继续、改稿或回退

- 通过且用户要继续 → 进入下一环。
- 关键选择未确认 → 给 2–3 个真正不同的方向，让用户选；不要抛一串术语问题。
- 某个上游产物被下游证明确有缺口 → 回到负责该产物的 skill 修改，只重做受影响的下游产物。
- 创作者本人卡住 → 暂停流水线，调用 `stc-first-aid`；解卡后回到原阶段。

用户要求实际改稿时：

1. 用 `stc-diagnose` 找到最影响整部作品的问题。
2. 先修改最上游、最能改变结果的一层，不从台词润色开始。
3. 调用对应创作 skill 生成修订产物；必要时继续向下重做受影响部分。
4. 交付修改后的故事、结构或正文，并用简短说明列出改了什么、为什么；不要让用户自己照着诊断单施工。

诊断后的回退责任：

| 诊断发现 | 回到谁 | 重做什么 |
|---|---|---|
| 主角、难题、起终变化、双目标或主题不成立 | `stc-idea-check` | 故事核心卡 |
| 三个世界、十五拍或整体转变不成立 | `stc-beatsheet` | 结构大纲 |
| 单场缺冲突、变化或因果 | `stc-scene-cards` | 受影响的场景卡 |
| 动作、潜台词或人物声音不成立 | `stc-scene-write` | 受影响的场景正文 |

上游产物发生改变后，明确列出哪些下游文件失效；只重做受影响部分，不全盘覆盖。

## 作品目录与断点续作

用户给了目录就沿用。没有目录但任务会跨多轮时，先确定一个可保留的作品目录。推荐产物名：

```text
<作品目录>/
├── 01-story-core.md
├── 02-beatsheet.md
├── 03-scene-cards.md
├── 04-scenes/
└── 05-revision-plan.md
```

每次继续先读现有产物，报告“目前到哪一步、下一步是什么”。不得让用户重新讲一遍，也不得用新一轮生成覆盖已经确认的决定；要改就明确记录变更。

## 面向小白的交互

- 先说“现在我们在做什么、做完会得到什么”，再提必要问题。
- 首次出现专业词时用一句人话解释。例如：“打破原生活的那件事，书里叫催化剂”。
- 默认一次只推进一个阶段；用户要求一口气完成时再连续运行。
- 不把检查清单当创作本身。先让故事长出来，再在正确阶段检查它。
- 按作品体量做取舍，不为覆盖术语增加无必要的支线和事件。

## 边界

- 本 skill 不亲自写故事核心、十五拍、场景卡、场景正文或诊断报告。
- 本 skill 到故事正文与改稿流程结束，不进入镜头设计、生成提示词或视频生成。
- 对外推介、经纪人和编剧职业经营不是完整创作流程的必经阶段，不塞进本 skill。
- 所有方法出处与整理者延伸见 `../references/source-ledger.md`。
